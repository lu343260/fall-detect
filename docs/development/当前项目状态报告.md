# AI-Fall-Detection-System 当前项目状态报告

> 报告日期：2026-08-27  
> 依据：项目根目录 `AGENTS.md`、`docs/` 文档、当前代码、Git 提交记录和已有实验输出。

## 1. 执行摘要

项目已经完成从基础跌倒规则原型到 YOLO11n-Pose + ONNX + 龙芯 2K0300 部署验证的主要工程链路，当前处于“算法与低算力部署优化验证阶段”。

当前最重要的事实是：

- 检测流程、状态机、ONNX 推理和龙芯运行时已经打通；
- 256×256 是当前已验证的较优输入尺寸，但龙芯上仍约为 0.23～0.24 FPS；
- ONNX Runtime 的目标板快速测试约比 OpenCV DNN 快 17.8%，但正式、可复现的 benchmark CSV 仍需补齐；
- INT8 模型大小减少约 72%，但当前没有证明能提升龙芯推理速度；
- 当前没有完整标注数据集，因此不能对准确率、召回率、误报率或漏报率下结论；
- 下一阶段最值得投入的方向是“统一性能基线 + 场景化检测评估”，随后再决定模型/后端优化路线。

## 2. 当前系统能力

### 2.1 检测与状态机

当前处理链路为：

```text
摄像头/视频
  → 图像预处理与 YOLO11n-Pose
  → 17 个人体关键点
  → 关键点置信度筛选
  → 髋部速度、髋部下降量、身体角度、身体宽高比
  → 多帧确认的跌倒状态机
  → 结果显示与性能日志
```

状态机已经包含 `INITIALIZING`、`NORMAL`、`FALLING` 和 `ON_GROUND` 等阶段，并使用初始化基线、多帧确认和恢复确认降低瞬时抖动造成的误判。

### 2.2 推理与部署

- 已完成 YOLO11n-Pose 的 PyTorch 到固定尺寸 ONNX 导出与结果验证。
- 已有通用 ONNX 推理路径和龙芯运行时部署目录。
- `deploy_loongson/` 保留较早的常规输入尺寸部署版本。
- `deploy_loongson_256/` 是当前重点版本，包含 256×256 模型、摄像头入口、跳帧、性能日志和 benchmark 工具。
- OpenCV DNN 已在龙芯平台完成运行；ONNX Runtime 已有目标板后端对比实验记录。
- 摄像头采集与推理目前仍在同一主循环中，尚未完成“采集线程 + 最新帧 + 推理线程”的解耦。

## 3. 已验证性能基线

以下数据来自已有报告，不同测试批次的 warmup、系统负载和统计口径可能不同，正式比较应重新统一测量。

| 方案 | 平台/输入 | 已记录结果 | 判断 |
|---|---|---:|---|
| OpenCV DNN FP32 | 龙芯 / 640×640 | 约 24.7 秒/帧 | 不可用 |
| OpenCV DNN FP32 | 龙芯 / 320×320 | 约 6.2 秒/帧 | 仍很慢 |
| OpenCV DNN FP32 | 龙芯 / 256×256 | 约 4.10～4.2 秒/帧，0.23～0.24 FPS | 当前 OpenCV 路径基线 |
| ONNX Runtime FP32 | 龙芯 / 256×256 | 快速测试约 3.45 秒/帧，0.29 FPS | 有加速迹象，待正式复测 |
| OpenCV DNN INT8 | 龙芯 / 256×256 | 约 4.27 秒/帧，约 0.23 FPS | 未产生速度收益 |

补充结论：

- 输入尺寸从 640 降到 256 是目前收益最明确的优化；
- OpenCV DNN 线程数从 1 增加到 2 的收益约 1.7%，4/8 线程反而变慢；
- `FRAME_SKIP` 能减少 YOLO 调用次数，但不降低单次推理延迟；
- Windows/AMD64 历史记录约为 21～22 FPS、平均推理约 31～34 ms，只能作为开发机基线，不能代表龙芯性能。

## 4. 检测效果证据边界

目前已有：

- 站立、坐下、跌倒等少量人工测试记录；
- 已知问题：侧身弯腰仍可能误报；
- 60 张图片上的 FP32/INT8 顶部检测关键点输出对比；关键点坐标误差约 1.28～2.63 px。

目前尚未形成：

- 跌倒/非跌倒标注集；
- 准确率、精确率、召回率、F1、误报率、漏报率；
- 首次告警延迟和恢复延迟；
- 不同视角、遮挡、光照、距离和多人场景的回归结果。

因此，当前只能确认“模型和规则链路能够工作”，不能确认“系统已经可靠识别跌倒”。关键点输出一致性也不能替代完整检测准确率。

## 5. 当前主要风险

### 高风险：实时性不足

龙芯 2K0300 上 256×256 仍只有约 0.24 FPS。跳帧可以降低调用频率，但会放大检测延迟，无法单独解决实时性问题。

### 高风险：检测质量证据不足

侧身弯腰误报已经出现，但目前缺少足够样本判断是阈值、状态机、关键点质量还是模型本身导致。

### 中风险：性能数据尚未完全统一

报告中规划了 `benchmark/results/backend_compare.csv`，但当前工作区没有看到该正式输出文件。ONNX Runtime 的 17.8% 优势应先按统一参数复测后再作为稳定基线。

### 中风险：部署代码存在重复路径

主目录、`deploy_loongson/` 和 `deploy_loongson_256/` 存在相似推理、状态机和结果兼容代码。后续修改状态机或接口时，容易出现版本漂移。

### 低风险：工作区存在未提交变更

当前工作区包含：

- `AGENTS.md` 和 `docs/README.md` 新增；
- 原有 `docs` 文件按分类移动后的未暂存状态；
- `deploy_loongson_256/yolo11n-pose-256-int8.onnx` 未跟踪。

这些变更没有在本报告中自动提交或删除。

## 6. 下一阶段最值得优化的方向

### 第一优先级：建立统一可信的性能与效果基线

这是当前投入产出比最高的方向。先不要继续凭单个实验结果扩展优化结论。

应在龙芯目标板使用相同模型、相同输入、相同 warmup、相同 iteration 和线程配置，统一测量：

1. OpenCV DNN FP32；
2. ONNX Runtime FP32；
3. OpenCV DNN INT8；
4. `setInput`、`forward`、后处理和端到端耗时；
5. CPU、内存、推理次数、最新帧延迟；
6. 实际运行日志和原始 CSV。

同时建立最小场景集：站立、坐下、弯腰、正面跌倒、侧面跌倒、缓慢倒地、遮挡、无人和恢复。记录真实标签、预测标签、误报/漏报和告警时间。

验收标准：能够用一条明确命令重复生成性能 CSV，并能够输出一张有样本数量支撑的检测指标表。

### 第二优先级：处理侧身弯腰误报

基于场景集回放，分别分析：

- 身体角度；
- 身体宽高比；
- 髋部下降量；
- 髋部下降速度；
- 倒地持续时间；
- 关键点置信度和缺失情况。

优先通过数据确认误报根因，再调整状态机门槛或增加必要特征。不要只通过堆叠条件压制单个样本。

### 第三优先级：确定实时性路线

如果产品目标是龙芯上接近实时运行，当前 YOLO11n-Pose 256×256 路线很可能仍然过重。应评估：

- 更轻量的 Pose 模型；
- 192×192、160×160 等更小输入；
- 人体检测 + 轻量跌倒分类器；
- 是否存在可用的龙芯硬件加速后端；
- OpenCV/ONNX Runtime 是否真正使用 LSX/LASX 或其他优化 kernel。

模型或后端更换必须同时比较速度和检测效果，不能只看 FPS。

### 第四优先级：最新帧线程架构

在单次推理路径确定后，再实现：

```text
摄像头采集线程
  → 只保留最新帧
  → 推理线程
  → 跌倒状态机
  → UI/声音/设备告警
```

该架构可以减少旧帧积压和界面阻塞，但不能替代模型与算子优化，优先级低于统一基线和轻量模型评估。

## 7. 建议的阶段性验收目标

### 阶段 A：证据闭环

- 生成正式的 OpenCV DNN/ONNX Runtime/INT8 对比 CSV；
- 固定目标板、模型、输入和测试参数；
- 建立第一版带标签场景集；
- 输出误报、漏报和告警延迟统计。

### 阶段 B：算法修正

- 复现并降低侧身弯腰误报；
- 保证正面/侧面跌倒仍能触发；
- 增加状态机回归测试，避免每次改阈值后靠人工重新判断。

### 阶段 C：实时性优化决策

- 如果 ORT 或算子优化不能把单帧延迟降到可接受范围，转向更轻量模型或专用后端；
- 只有在单帧性能达到合理水平后，才评估线程解耦和自适应跳帧；
- 每次优化都必须同时保存速度和检测效果结果。

## 8. 结论

项目已经完成了较扎实的工程化起步，核心价值在于：状态机、ONNX 链路、龙芯部署、输入尺寸实验、跳帧和性能日志均已形成可继续迭代的基础。

但当前最关键的瓶颈不是代码功能缺失，而是“实时性不足”和“检测效果证据不足”。下一阶段最值得做的不是继续增加零散优化，而是先建立统一 benchmark 和场景化评估，然后依据数据选择轻量模型、推理后端或算子优化路线。
