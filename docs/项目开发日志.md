# AI-Fall-Detection-System 项目开发日志

> 整理依据：项目当前代码、`docs/` 下已有文档，以及 Git 提交记录（截至 2026-08-12）。
>
> 说明：日志按提交时间顺序归纳开发阶段；同一天内按实际提交先后排列。性能数据只记录仓库中已有实测结果，不对未测量的精度、功耗或端到端延迟作推断。

## 项目演进概览

项目从基于 YOLO Pose 的基础人体姿态检测开始，逐步加入跌倒状态机、初始化校准、髋部运动特征和多帧确认机制；随后将 YOLOv8 Pose 升级为 YOLO11n-Pose，并完成 ONNX 推理、龙芯 2K0300 运行时部署、256×256 输入尺寸优化和跳帧/性能日志能力。

整体处理链路为：

```text
摄像头读取 → 图像旋转/预处理 → YOLO Pose 获取人体关键点
→ 关键点置信度筛选 → 髋部速度/下降量/身体角度/宽高比计算
→ 跌倒状态机 → 结果显示与性能记录
```

## 第一阶段：基础跌倒检测与状态机建立

### 2026-07-27

- **开发目标**：在已有 YOLO Pose 人体关键点检测基础上，实现基础跌倒识别流程。
- **实现内容**：增加 `FallDetector`，并在 `pose_video.py` 中接入视频/摄像头检测；使用人体关键点计算身体宽高比、身体倾斜角度和髋部位置，输出跌倒判断结果。同期清理无关学习文件、缓存文件并补充 `.gitignore`。
- **技术方案**：采用规则驱动的初版状态机，将连续视频帧中的姿态特征转换为跌倒状态，保持检测和显示流程分离。
- **遇到的问题**：单帧规则容易受到关键点抖动和瞬时姿态变化影响，程序启动瞬间也可能出现误报警。
- **解决方法**：引入基础状态管理，为后续增加持续时间和多帧确认预留结构；将缓存等运行产物从版本管理中移除。
- **优化效果**：形成可运行的基础跌倒检测闭环，项目结构和版本库更加干净。
- **后续计划**：继续细化状态转换条件，降低误报和漏报。

### 2026-07-31

- **开发目标**：优化跌倒检测状态机逻辑，使状态转换更稳定。
- **实现内容**：调整 `fall_detector.py` 和 `pose_video.py` 中的状态判断与时间处理逻辑，明确正常、跌倒过程和倒地等阶段。
- **技术方案**：采用显式状态而不是单个布尔值表示检测结果，并将状态转换条件集中在检测器内部。
- **遇到的问题**：姿态特征在临界值附近波动时，状态可能反复切换。
- **解决方法**：补充状态持续条件和更清晰的分支逻辑，减少由单帧异常造成的状态跳转。
- **优化效果**：状态机具备了进一步加入多帧确认、恢复逻辑的基础。
- **后续计划**：增加连续帧确认机制，并完善跌倒后的恢复判断。

## 第二阶段：多帧确认、初始化校准与运动特征增强

### 2026-08-01

- **开发目标**：避免单帧异常直接触发跌倒。
- **实现内容**：增加 `falling_frames`、`ground_frames` 等计数器，要求快速下落和倒地条件分别连续满足若干帧后才确认状态。
- **技术方案**：采用“满足条件累加、不满足条件衰减或清零”的多帧确认策略。
- **遇到的问题**：摄像头噪声、关键点抖动和短暂遮挡会导致某一帧特征异常。
- **解决方法**：将跌倒开始和倒地确认拆成独立的连续帧门槛，避免一次异常检测立即报警。
- **优化效果**：降低了瞬时误报，状态转换更加平滑。
- **后续计划**：为不同使用场景增加正常姿态基线，减少固定阈值对摄像头位置和人体初始姿态的依赖。

### 2026-08-03

- **开发目标**：解决固定阈值难以适配不同摄像头视角的问题，并增强对“髋部下沉”的识别能力。
- **实现内容**：
  - 增加初始化校准阶段，状态初始为 `INITIALIZING`，先采集稳定人体姿态；
  - 收集 10 个平滑后的髋部 y 坐标样本，标准差小于 10 时以中位数建立 `baseline_hip_y`；不稳定时清空并重新采样；
  - 在跌倒判断中加入髋部相对基线的下降量 `hip_drop`；
  - 将髋部下降速度与髋部下降量组合使用，判断快速下落事件。
- **技术方案**：以左右髋部关键点（COCO-17 索引 11、12）的中心 y 坐标作为主要垂直运动特征；使用滑动平均抑制关键点抖动，使用中位数建立更稳健的初始基线。
- **遇到的问题**：启动时没有可靠基线，直接计算下降量会导致误报；仅使用身体角度或宽高比又难以区分弯腰、坐下和跌倒。
- **解决方法**：校准完成前禁止速度、角度和 `hip_drop` 参与跌倒判断；正常状态下再以较小比例缓慢更新基线，适应人体位置的缓慢变化。
- **优化效果**：检测从绝对位置判断转向相对初始姿态判断，对场景差异更有适应性；髋部下沉为跌倒识别增加了明确的时空特征。
- **后续计划**：继续处理无人状态、关键点缺失和基线被异常姿态污染等情况。

### 2026-08-04

- **开发目标**：修复无人或暂时没有有效人体时的检测窗口与时间传递问题。
- **实现内容**：调整无人体情况下的处理逻辑，并完善检测时间参数在视频循环和状态机之间的传递。
- **技术方案**：使用单调时钟 `time.monotonic()` 作为跌倒速度和持续时间计算依据，避免系统时间回拨或调整影响计时。
- **遇到的问题**：检测不到人时仍需保持画面刷新；使用不稳定的时间来源可能使速度或持续时间计算异常。
- **解决方法**：将“画面显示”和“有效人体状态更新”分开；只有关键点有效时才推进跌倒检测，时间统一使用单调时钟。
- **优化效果**：无人场景下程序不会因检测窗口异常中断，持续时间和髋部速度计算更可靠。
- **后续计划**：加入关键点置信度检查和髋部轨迹平滑。

### 2026-08-08：状态机稳定性与 YOLO11n-Pose 升级

- **开发目标**：完善跌倒后的恢复逻辑，减少关键点抖动影响，并升级姿态模型。
- **实现内容**：
  - 增加髋部关键点平滑历史队列；
  - 将恢复正常也改为连续多帧确认，并在恢复时清理相关计数和历史；
  - 增加髋部间距离输出，辅助调试和后续尺度分析；
  - 将模型从 YOLOv8 Pose 切换为 `yolo11n-pose.pt` / YOLO11n-Pose。
- **技术方案**：检测时同时保留两类髋部特征：平滑髋部位置用于基线下降量，原始髋部位置用于保留快速下降响应；状态包括 `INITIALIZING`、`NORMAL`、`FALLING`、`ON_GROUND`，恢复需要连续满足站立条件。
- **遇到的问题**：跌倒后短暂站起或关键点抖动可能造成误恢复；模型升级后需要确认原有关键点接口和检测流程仍然兼容。
- **解决方法**：增加 `recovery_frames` 和恢复确认帧数；继续使用 `keypoints.xy`、`keypoints.conf` 接口；通过 ONNX 导出与验证脚本检查 YOLO11 输出。
- **优化效果**：跌倒、倒地、恢复之间的状态转换更稳定；模型能力升级，同时保留了原有后处理接口。
- **后续计划**：将 PyTorch 推理替换为更适合部署的 ONNX 推理，并验证输出一致性。

## 第三阶段：ONNX 推理与龙芯 2K0300 部署

### 2026-08-08 至 2026-08-09：ONNX 转换和推理链路替换

- **开发目标**：去除部署端对 PyTorch/Ultralytics 完整运行环境的依赖，为龙芯平台部署做准备。
- **实现内容**：
  - 使用 `export_onnx.py` 将 YOLO11n-Pose 模型导出为固定输入尺寸 ONNX；
  - 使用 `onnx_test.py` 对 ONNX 与 `.pt` 推理结果进行验证和关键点对比；
  - 新增 `onnx_inference.py`，封装 letterbox、BGR/RGB 转换、归一化、ONNX Runtime 推理、NMS 和坐标还原；
  - 保持结果接口兼容 `results[0].keypoints.xy`、`keypoints.conf` 和 `plot()`。
- **技术方案**：固定输入尺寸、静态 ONNX 图、opset 12、模型简化；后处理复用 Ultralytics 的 NMS 和坐标缩放逻辑，避免更换推理后改变跌倒检测输入语义。
- **遇到的问题**：ONNX 输出格式与 Ultralytics 高层结果对象不同，且预处理/坐标还原不一致会直接影响髋部位置和角度计算。
- **解决方法**：实现兼容层 `PoseResult`/`Keypoints`，统一输出 `(N,17,2)` 和 `(N,17)`；通过独立验证脚本比较 ONNX 与 `.pt` 的人体框和髋部关键点。
- **优化效果**：主程序可使用 ONNX Runtime 完成姿态推理，推理模块与跌倒状态机解耦，便于跨平台部署。
- **后续计划**：制作龙芯 2K0300 的运行时目录，并实测不同输入尺寸的推理性能。

### 2026-08-09

- **开发目标**：在龙芯 2K0300 上建立可直接运行的 YOLO11n-Pose ONNX 部署包。
- **实现内容**：新增 `deploy_loongson/`，包含运行时推理代码、状态机、入口程序、依赖说明和 `yolo11n-pose.onnx`；部署端不包含训练、导出或 PyTorch 模型依赖。
- **技术方案**：使用 ONNX Runtime CPUExecutionProvider；保留与主项目一致的跌倒检测器和关键点结果接口，支持摄像头入口、旋转、无显示和按间隔处理等运行选项。
- **遇到的问题**：龙芯平台计算资源有限，直接使用 640×640 输入时推理速度很慢；同时需要保证部署版本和主项目状态机行为一致。
- **解决方法**：将模型和运行时脚本独立打包，先完成 640×640 部署基线，再准备固定尺寸模型和性能测试工具。
- **优化效果**：形成可复制的龙芯运行时部署版本，降低部署环境复杂度。
- **后续计划**：比较 640、320、256 等输入尺寸，并选择速度与检测效果之间的合适平衡点。

### 2026-08-10 至 2026-08-11：固定输入尺寸与性能基线

- **开发目标**：量化输入尺寸对龙芯 2K0300 推理速度的影响，并生成独立模型文件。
- **实现内容**：完善固定尺寸导出和 `onnx_size_benchmark.py` 基准测试工具，生成 `yolo11n-pose-320.onnx`；在龙芯上进行部署和推理耗时测试。
- **技术方案**：导出时关闭动态尺寸，分别生成带尺寸后缀的 ONNX 文件，避免不同尺寸模型发生文件名覆盖；比较单帧推理耗时和近似 FPS。
- **遇到的问题**：640×640 模型在龙芯上单帧耗时约 25 秒，无法满足视频应用需求；不同输入尺寸需要确保预处理和后处理的尺寸常量同步。
- **解决方法**：将输入尺寸作为导出和推理配置的一部分，并为不同尺寸建立独立部署/测试路径。
- **优化效果**：已有实测结果显示：640×640 约 25 秒/帧（约 0.04 FPS），320×320 约 6.2 秒/帧（约 0.16 FPS），输入尺寸下降带来明显速度提升。
- **后续计划**：继续尝试 256×256，并修复龙芯 OpenCV DNN/输入管线兼容问题。

## 第四阶段：256×256 龙芯部署、跳帧和性能日志

### 2026-08-12：256×256 部署版本

- **开发目标**：在保证运行链路完整的前提下，进一步降低龙芯 2K0300 的单帧推理开销。
- **实现内容**：新增独立目录 `deploy_loongson_256/`，包含 `yolo11n-pose-256.onnx`、推理模块、摄像头入口和依赖说明；主程序在 LoongArch 平台自动选择 256 模型和 `INPUT_SIZE=256`。
- **技术方案**：固定 256×256 输入，独立管理模型与部署代码，不覆盖原有龙芯部署目录；保持关键点输出和状态机代码兼容。
- **遇到的问题**：256 输入管线在龙芯平台出现输入形状/预处理兼容问题，不能仅通过更换模型文件完成部署。
- **解决方法**：连续修复 256 版本输入流程，调整 ONNX 推理实现并引入 OpenCV DNN 路径适配；同步清理不再需要的依赖。
- **优化效果**：256 模型可以在龙芯 2K0300 上正常加载并进行人体姿态检测；已有实测约 4.2 秒/帧，约 0.24 FPS，相比 320 和 640 更快，但仍未达到流畅实时视频速度。
- **后续计划**：继续优化 CPU 推理、预处理和后处理，并结合真实场景评估输入尺寸降低后的检测精度。

### 2026-08-12：跳帧策略优化

- **开发目标**：在摄像头持续取帧的同时减少昂贵的 YOLO 推理次数，改善低算力平台上的整体响应。
- **实现内容**：增加 `FRAME_SKIP` 配置；摄像头仍逐帧读取，但只在满足间隔的帧执行姿态推理；画面显示、摄像头 FPS 和最近一次推理结果保持连续更新；状态机调用继续按有效关键点和既定帧条件执行。
- **技术方案**：将采集频率与 AI 推理频率解耦，使用固定跳帧策略；在画面上显示 `CameraFPS`、`Inference Time`、`Skip` 和 `AI FPS`，便于现场调参。
- **遇到的问题**：直接减少读取帧会导致画面卡顿或时间语义失真；跳帧后需要明确推理帧数、状态机调用次数和摄像头帧率的区别。
- **解决方法**：保持摄像头逐帧读取，只跳过模型调用；检测时间使用帧读取时的单调时间；将摄像头 FPS 与 AI FPS 分开统计。
- **优化效果**：降低了理论推理调用频率，并为不同 `FRAME_SKIP` 设置提供可比较的实验入口；不会因为跳帧而停止画面刷新。
- **后续计划**：在龙芯实测中比较不同跳帧间隔对延迟、漏检和跌倒确认时间的影响，必要时采用自适应跳帧。

### 2026-08-12：跨平台性能日志与输入管线修复

- **开发目标**：建立可追踪的性能实验记录，并收敛 256 版本在龙芯上的输入兼容问题。
- **实现内容**：新增 `performance_logger.py`，使用 Python 标准库按固定时间间隔记录平台、模型、输入尺寸、跳帧数、摄像头 FPS、AI FPS、推理次数及平均/最大/最小耗时；生成 `performance_log.csv`；完善龙芯 256 输入管线和 OpenCV DNN 适配。
- **技术方案**：性能日志采用跨平台 CSV 格式，默认每 5 秒写入一次；模型和输入尺寸由平台自动选择：普通平台使用 `yolo11n-pose.onnx`/640，LoongArch 使用 `yolo11n-pose-256.onnx`/256。
- **遇到的问题**：性能数据需要同时覆盖 Windows/AMD64 和 LoongArch；输入管线的实现差异可能造成模型能加载但无法正确推理。
- **解决方法**：将平台信息和实验参数写入同一条日志；针对 256 模型继续调整 OpenCV DNN 输入与推理路径，保留独立的龙芯部署目录。
- **优化效果**：当前仓库已有 Windows/AMD64 记录：摄像头约 21～22 FPS、AI FPS 约 21 FPS，平均推理耗时约 31～34 ms；龙芯 256 版本的模型加载和姿态推理链路已打通。
- **后续计划**：补充龙芯不同跳帧参数的长期 CSV 数据，并建立统一的端到端延迟、检测准确性和资源占用评估方法。

## LoongArch LSX/LASX 优化探索现状

- **完成日期**：截至 2026-08-12，项目代码和文档中未发现已经落地的 LSX/LASX intrinsic、汇编内核或编译器向量化实现。
- **当前状态**：本阶段主要完成了 LoongArch 平台适配、ONNX/OpenCV DNN 输入管线修复、256×256 模型和跳帧策略；这些属于部署路径与算法调用层优化，不应表述为 LSX/LASX 已完成加速。
- **后续计划**：
  1. 先通过性能日志定位预处理、DNN 推理、NMS、关键点后处理和显示环节的耗时占比；
  2. 在龙芯工具链和 OpenCV/ONNX Runtime 构建条件允许时，验证 LSX/LASX 自动向量化和手工 intrinsic 的收益；
  3. 优先评估图像归一化、NHWC/NCHW 重排、resize/letterbox 等连续数据处理环节；
  4. 对比开启向量化前后的精度、稳定性、功耗和端到端延迟，只有实测有效后再合入正式部署版本。

## 当前项目状态与总体后续计划

截至 2026-08-12，项目已经具备：

- YOLO11n-Pose 姿态检测模型及 PyTorch/ONNX 转换验证链路；
- 基于初始化基线、髋部速度、髋部下降量、身体角度和宽高比的跌倒检测；
- `INITIALIZING → NORMAL → FALLING → ON_GROUND` 状态机及多帧恢复确认；
- 摄像头实时读取、画面绘制、摄像头 FPS 与 AI FPS 分离统计；
- 龙芯 2K0300 的 640、320、256 输入尺寸部署演进，其中 256 版本约 4.2 秒/帧；
- 固定跳帧参数和跨平台 CSV 性能记录能力。
