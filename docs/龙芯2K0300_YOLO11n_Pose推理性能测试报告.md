# 龙芯 2K0300 YOLO11n-Pose 推理性能测试报告

## 1. 测试概述

### 1.1 项目与测试对象

- **项目**：基于 LoongArch 架构的适老机器宠物智能终端
- **测试对象**：YOLO11n-Pose ONNX 模型及其 256×256 INT8 量化版本
- **目标平台**：龙芯 2K0300 先锋派
- **测试类型**：OpenCV DNN / ONNX Runtime CPU 推理、输入尺寸、线程数和 INT8 量化对比
- **测试时间**：2026-08-09 至 2026-08-12

本报告汇总 `E:/QQ/龙芯2K0300_YOLO11n_Pose推理性能测试报告.md` 和项目当前测试记录。模型推理性能与跌倒检测状态机是两个维度：本报告重点评估模型加载、前向推理和部署性能，不把单次姿态输出误差等同于完整跌倒检测准确率。

### 1.2 测试目标

1. 验证 YOLO11n-Pose ONNX 模型能否在龙芯 2K0300 上正常加载和推理；
2. 建立 640×640、320×320 和 256×256 输入尺寸的性能基线；
3. 对比 OpenCV DNN 与 ONNX Runtime CPU 后端；
4. 验证 OpenCV DNN 线程数对单核环境推理速度的影响；
5. 评估 INT8 量化对模型大小、关键点输出和推理耗时的影响；
6. 为后续 LoongArch 算子优化、轻量化模型和实时系统架构提供依据。

## 3. 模型与推理链路

### 3.1 模型输入输出

原始固定尺寸模型：

```text
model: yolo11n-pose.onnx
input: images / float32 / 1×3×640×640
output: output0 / 1×56×8400
```

固定尺寸模型的输出通道为：4 个检测框参数、1 个类别置信度和 17 个关键点的 51 个参数，共 56 个通道。

项目后续导出 320×320 和 256×256 固定尺寸模型，输出网格随输入尺寸降低：

| 输入尺寸 | 输出 Shape | 输入面积相对 640×640 |
|---:|---:|---:|
| 640×640 | `1×56×8400` | 100% |
| 320×320 | `1×56×2100` | 25% |
| 256×256 | `1×56×1344`（以实际模型输出为准） | 16% |

### 3.2 OpenCV DNN 推理流程

```text
摄像头帧
→ letterbox
→ BGR 转 RGB / 归一化 / NCHW
→ OpenCV DNN net.forward()
→ NMS 和坐标还原
→ 17 点人体姿态
→ 跌倒状态机
```

部署端通过 `keypoints.xy` 和 `keypoints.conf` 保持与原 YOLO 接口兼容，避免更换推理后端时修改跌倒检测器。

### 3.3 ONNX Runtime 适配

外部测试使用针对龙芯 2K0300 重新构建的 ONNX Runtime 1.17.1。由于目标环境的 MLAS SIMD 路径存在硬件能力假设问题，运行时采用：

```text
MLAS_FORCE_SCALAR=ON
```

并使用 C API benchmark，固定输入为 `1×3×640×640` FP32，避免旧 C++ Wrapper 元数据查询异常和 Python 数据转换干扰。

典型动态库信息：

```text
/usr/lib/libonnxruntime.so.1.17.1
ORT_API_VERSION: 17
```

### 4.3 后端对比

| 指标 | OpenCV DNN | ONNX Runtime |
|---|---:|---:|
| 输入尺寸 | 640×640 | 640×640 |
| 数据类型 | FP32 | FP32 |
| CPU 线程 | 1 | intra/inter 均为 1 |

## 7. OpenCV DNN 线程数实验

### 7.1 实验目的与配置

针对龙芯 2K0300 单核环境，对 OpenCV DNN CPU 推理线程数进行对比。测试保持模型、输入尺寸、摄像头分辨率和无显示配置一致，比较 `--dnn-threads 1` 与 `--dnn-threads 2`。

### 7.2 测试结果

| OpenCV DNN 线程数 | 平均推理耗时 | FPS（约） |
|---:|---:|---:|
| 1 | ≈4500 ms | 0.22 |
| 2 | ≈4650 ms | 0.21 |

线程数从 1 增加到 2 后，平均耗时增加约 150 ms，约增加 3.3%；FPS 从约 0.22 降至约 0.21。截图中的连续日志也显示单线程约 4.47～4.52 秒，双线程约 4.62～4.70 秒，趋势较稳定。

### 7.3 结论

在当前单核硬件上，多线程没有产生并行计算收益，线程调度、任务切分和同步开销反而增加了总耗时。因此当前部署采用单线程推理配置。

该结论适用于当前单核龙芯平台和 OpenCV DNN CPU 路径，不代表多核龙芯平台或其他 OpenCV 后端同样如此。后续如更换硬件，应重新测试线程数。

### 7.4 最新 OpenCV DNN 线程 benchmark 结果

在 LoongArch 平台上，针对 `yolo11n-pose-256.onnx`、`256×256` 输入、
OpenCV DNN CPU 推理路径，对 1、2、4、8 个线程进行了统一 benchmark。
本次实验直接统计 `net.forward()` 平均耗时和对应 FPS，结果如下：

| OpenCV DNN 线程数 | 平均 forward 耗时 | FPS |
|---:|---:|---:|
| 1 | 3926.840 ms | 0.255 |
| 2 | 3858.437 ms | 0.259 |
| 4 | 4146.693 ms | 0.241 |
| 8 | 4705.376 ms | 0.213 |

结果表明，线程数并非越多越快。2 线程相比 1 线程的平均推理耗时降低约
1.7%，FPS 提升约 1.6%；继续增加线程数后，线程调度、同步以及计算资源
竞争带来的开销超过了并行收益，导致整体性能下降。因此，当前 LoongArch
单核部署环境最终选择 2 个 OpenCV DNN 线程作为部署配置。

本节结果以 `benchmark/results/opencv_thread_benchmark.csv` 为依据，
覆盖并更新前文早期的线程数试验结果。该结论适用于当前 LoongArch
2K0300 硬件、OpenCV DNN CPU 后端和 256x256 模型；更换硬件或后端后应
重新进行线程数测试。

## 8. INT8 量化实验

### 8.1 实验目的

评估 YOLO11n-Pose 256×256 模型进行 INT8 量化后，对模型存储空间、关键点输出和龙芯 2K0300 CPU 推理速度的影响。

### 8.2 测试结果

| 指标 | FP32 | INT8 | 变化 |
|---|---:|---:|---:|
| 单帧推理耗时 | 4.10 秒 | 4.27 秒 | 增加约 0.17 秒，约 4.1% |
| 近似 FPS | 0.24 | 0.23 | 略有下降 |
| 模型大小 | 11.09 MiB | 3.10 MiB | 减少约 72.0% |
| 关键点误差 | — | 小于 3 px | 误差较小 |

关键点误差为量化模型与 FP32 模型输出之间的对比结果，尚不等同于完整数据集上的检测精度指标。

### 8.3 结论与分析

INT8 量化将模型从 11.09 MiB 降至 3.10 MiB，显著降低存储和传输需求；关键点误差小于 3 px，当前对比中姿态定位结果基本保持稳定。

但是，当前 OpenCV DNN CPU 执行路径下 INT8 推理约 4.27 秒/帧，慢于 FP32 的 4.10 秒/帧，未产生速度收益。可能原因包括：

- OpenCV DNN 当前执行路径未使用针对龙芯的高效 INT8 kernel；
- 算子之间存在量化/反量化操作；
- INT8 数据格式转换和内存拷贝带来额外开销；
- 当前模型算子结构与 CPU 后端的 INT8 优化覆盖度不高。

因此，INT8 当前主要体现为存储优化，而不是推理加速优化。是否能够通过 INT8 获得速度收益，需要结合算子级 profiling、后端 kernel 支持和量化模型格式继续验证。

## 9. 已发现问题及处理

### 9.1 OpenCV HighGUI 缺失

目标系统的 OpenCV 构建未包含 HighGUI 时，调用 `cv2.namedWindow()` 会失败。该问题不影响 OpenCV DNN、VideoCapture、图像处理和无显示推理。当前测试使用 `--no-display` 绕开；产品界面可由 Qt6 独立负责。

### 9.2 ONNX Runtime 元数据查询异常

早期 benchmark 出现 `Expected FP32 input tensor`、`std::bad_alloc` 和 `cannot create std::vector larger than max_size()` 等错误。后续通过 ONNX Runtime C API、固定 1.17.1 Header/API、固定输入信息和明确动态库路径完成修复，最终确认 Session 创建、输入 Tensor 创建、Run 和输出 Shape 均正常。

### 9.3 低输入尺寸管线兼容问题

256×256 版本曾出现输入形状和预处理管线兼容问题。项目通过独立部署目录、固定输入配置、OpenCV DNN 输入路径调整和模型加载验证完成修复。

### 9.4 单核线程扩展无收益

增加 OpenCV DNN 线程数后耗时上升，因此当前选择单线程。该现象是单核平台的部署参数结论，不应泛化到多核平台。

## 10. 综合结果分析

### 10.1 主要瓶颈

当前性能瓶颈不是单一软件后端造成的，而是以下因素叠加：

```text
YOLO11n-Pose 计算量
+ 输入分辨率
+ 单核 1 GHz CPU
+ SIMD/算子后端支持情况
+ 内存访问与数据格式转换
```

640×640 从约 25 秒降低到 256×256 的约 4.2 秒，说明输入尺寸是当前最有效的已验证优化方向之一。ORT 在 640×640 上比 OpenCV DNN 快约 12.8%，但仍无法改变非实时结论。INT8 大幅降低模型大小，却没有降低当前 OpenCV DNN CPU 推理时间，说明模型压缩收益和算子执行收益并不等价。

### 10.2 当前方案的实时性判断

256×256 FP32 约 0.24 FPS，INT8 约 0.23 FPS，均远低于流畅视频检测所需帧率。跳帧可以降低单位时间内的推理调用次数，但不会降低单次推理延迟，因此只能缓解 CPU 负载和采集阻塞，不能单独实现实时跌倒检测。

### 10.3 精度结论边界

当前已确认的是模型能够输出人体关键点，以及 INT8 与 FP32 的关键点误差小于 3 px。尚未形成完整的跌倒、坐下、弯腰、侧身、遮挡、无人和恢复场景统计，因此不能据此给出准确率、召回率、误报率或实时告警延迟结论。

## 11. 后续优化计划

### 11.1 模型与算子优化

- 继续评估 192×192、160×160 等更小输入尺寸；
- 评估更轻量的 Pose 网络或面向跌倒状态的专用分类模型；
- 进行模型剪枝、结构化裁剪和算子融合；
- 检查 OpenCV DNN INT8 kernel 覆盖情况，定位量化/反量化开销；
- 对预处理、NCHW 重排、resize、后处理和内存拷贝进行耗时 profiling；
- 在确认硬件能力和工具链支持后，探索 LoongArch LSX/LASX 向量化，并以实测收益为准。

### 11.2 系统架构优化

当前不建议采用“读取一帧→阻塞推理→读取下一帧”的串行架构。建议采用：

```text
摄像头采集线程
        ↓
只保留最新帧
        ↓
AI 推理线程（固定跳帧或自适应跳帧）
        ↓
姿态结果 / 跌倒状态机
        ↓
Qt6 界面、声音、灯光和机器宠物控制
```

该架构可以避免摄像头缓冲积累旧画面，使状态机尽量处理最新数据；但它不能替代模型和算子优化，单次推理延迟仍需继续降低。

### 11.3 测试计划

1. 对 1、2、4 等线程数进行统一时长、多轮、去预热测试；
2. 为 640、320、256、192、160 建立统一的性能和精度数据表；
3. 对 FP32、INT8 进行算子级耗时和内存访问分析；
4. 建立跌倒、坐下、弯腰、侧身、遮挡、无人和恢复场景回归集；
5. 记录端到端延迟、CPU 占用、内存、功耗和检测准确率；
6. 分别验证 OpenCV DNN、ONNX Runtime 及可能的硬件加速后端。

## 12. 阶段性结论

### 已验证内容

1. OpenCV 4.10.0 DNN 可以在龙芯 2K0300 上加载并执行 YOLO11n-Pose ONNX；
2. ONNX Runtime 1.17.1 scalar MLAS 路径可以完成 640×640 FP32 推理；
3. USB 摄像头可以正常采集 640×480 图像；
4. 姿态检测链路能够输出人体框和 17 个关键点；
5. 640×640、320×320、256×256 模型均已完成不同程度的部署和性能验证；
6. 256×256 FP32 实测约 4.2 秒/帧，较 640×640 有明显改善；
7. 单核环境中 OpenCV DNN 单线程优于双线程；
8. INT8 模型大小降低约 72%，关键点误差小于 3 px；
9. 当前 OpenCV DNN CPU 路径下 INT8 未带来推理加速。

### 核心结论

> 在龙芯 2K0300 单核环境下，降低输入尺寸是目前最明确有效的速度优化手段；ONNX Runtime 在 640×640 基线上比 OpenCV DNN 快约 12.8%；INT8 量化显著降低模型存储需求，但当前 OpenCV DNN CPU 路径未产生速度收益。256×256 版本已经能够运行，但约 0.24 FPS 仍无法满足流畅实时跌倒检测。

## 13. 当前性能基线

```text
Platform:
  Loongson 2K0300 / LoongArch64
```
